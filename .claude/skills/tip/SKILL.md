# 手順

1. **テーマと slug を決める**: 引数がテーマ（`/tip OpenRouter`）。slug はファイル名かつ URL（`/tips/<slug>/`）で、使えるのは**英小文字・数字・ハイフンだけ**（`openrouter` / `mcp`）。まず既存を見て、同じテーマが無いか確かめる。

    ```sh
    head -5 docs/tips/*.md    # 全 Tips の title / description
    ```

    同じテーマが既にあれば**新しく作らず、その記事を直して `updated` を上げる**（slug を増やすと、どちらにリンクすべきか分からなくなる）。

2. **調べる**: 一次情報（公式ドキュメント・仕様・リポジトリ）にあたる。ブログや記事は補助。日本語版があっても英語版を読む。**裏が取れなかったことは書かない。**
3. **書く**: `docs/tips/<slug>.md`。frontmatter は 3 つだけ。

    ```yaml
    ---
    title: "OpenRouter とは"
    description: "複数の LLM を 1 つの API で呼び分けられる中継サービス。乗り換えとフォールバックのコストを下げる"
    updated: 2026-09-03
    ---
    ```

    - `description` は `/tips/` 一覧に出る 1 行。本文の書き出しを流用せず「**何が分かる記事か**」を書く
    - `updated` は書いた日（JST）。一覧はこの降順に並ぶ

4. **確認**: `npm run build` が通ること（frontmatter がスキーマに合わなければビルドが落ちる）。あわせて `npm run dev` で `/tips/` と `/tips/<slug>/` を目で見る。
5. **commit**: `git add docs/tips/<slug>.md && git commit -m "docs: <slug> の Tips を追加"`。**push はしない。**

# 書き方

読者は**その分野を知らない人**。その日のニュースではなく、日次レポートを読むための前提知識を置く場所。

- **1 記事 1 テーマ。** 「それは何なのか」に答えて終わる。関連する話を詰め込まない
- 本文は H2 区切り。目安は **何なのか / 何が嬉しいのか / どういうときに向くか（＋注意する点）**
- **良いところだけ書かない。** 向かない場面・コスト・注意点を必ず入れる。判断材料になることが Tips の値打ち
- 専門用語は初出の 1 回だけ `用語（15〜30 字のかみ砕いた説明）` で開く（[[daily-report]] の「# 専門用語の開き方」に揃える）
- **公式ドキュメントへのリンクを 1 本置く。** 料金・対応モデルなど変わり続けるものは書き写さず、リンクで渡す
- 長さは 1000〜2000 字。これを超えるならテーマが大きすぎる

# やらないこと

- **`docs/blog/` を書き換えない。** 過去のレポートに後からリンクを足さない。書いた Tips は、以降の [[daily-report]] が用語に合わせてリンクする（同スキルの「## Tips へのリンク」）
- **原文のコピー・逐語訳をしない**（[[daily-report]] の「# 引用と著作権のルール」と同じ）
- 既存 Tips の slug を変えない・消さない（レポート本文からのリンクが切れ、ビルドが落ちる）
