### [Introducing Muse Spark 1.3](https://research.meta.ai/blog/introducing-muse-spark-1-3)
<!-- categories: LLM, Meta, AI Agent -->

Metaが研究ブログで「Muse Spark 1.3」を発表し、Muse CodeとMeta Model APIで同日提供を始めた。前版の1.2からの改善点として挙げているのは、長時間の作業を続ける力と、1本の会話の中で複数の用件を並行して扱う力、そして自分に何ができて何ができないかを把握する精度だ。数字として明示されたのはコーディング時の効率で、外部ツールの呼び出し回数が約20%、消費トークン（AIが読み書きする文字数ぶんの従量課金の単位）が約25%減ったとしている。安全面では、取り消しのきかない操作を実行してよいかの判断を強化したと説明する。最も深く考えさせる「max reasoning」モードは追加の安全検証後に出す方針で、公開ウェイト版についても「今後のロードマップ」としか触れていない。手元のGPU 1枚で動く[Muse Glimmer](/blog/2026-08-11/#muse-glimmer--手元の1枚のgpuで動く30bのエージェント向けモデル)とは別系統の、エージェント本命ラインの更新にあたる。

### [Goroutine Leak Profiles](https://go.dev/blog/goroutine-leak-profiles)
<!-- categories: Go, Observability -->

Goの公式ブログが、Go 1.27に入った「ゴルーチンリーク検出プロファイル」を解説した。ゴルーチン（Goの軽量な並行処理の単位）が、二度と満たされない条件を待ち続けたまま残ってしまう状態を、本番環境で誤検出を抑えつつ見つけられるようにするものだ。使い方は`runtime/pprof`の`goroutineleak`プロファイル、または`net/http/pprof`の`/debug/pprof/goroutineleak`エンドポイントで、解析は既存の`go tool pprof`にそのまま乗る。仕組みが面白く、ガベージコレクタ（不要になったメモリを回収する仕組み）を転用して「止まっていないゴルーチンから辿り着けるか」を判定し、辿り着けなかったものをリークと見なす。チャネルやselect、`sync`のMutex・WaitGroup・Condでの待ちが対象で、ファイルやネットワークの入出力待ち、独自の待ち合わせ機構は検出できない。[Go 1.27のリリース記事](/blog/2026-08-20/#go-127-is-released)では新機能の1つとして名前が挙がるだけだったが、今回その仕組みと使い方がまとめて示された。長時間動かし続けるサーバーを持っているなら、真っ先に試す価値がある。

### [Read your own writes, off the primary](https://boringsql.com/posts/read-your-own-writes)
<!-- categories: PostgreSQL, Database -->

書き込みは親側（プライマリ）、読み取りは複製側（レプリカ）に振り分ける構成でよく起きる「自分が今保存したはずのデータが画面に出てこない」問題への対処法を、boringsqlの著者が整理した。原因は複製の遅れで、画面側の反応がミリ秒単位に速くなるほど目立つようになる。提案されているのは、PostgreSQL 19で入る`WAIT FOR LSN`を使うやり方だ。書き込み確定後に`pg_current_wal_flush_lsn()`でその時点の位置（LSN。更新履歴のどこまで進んだかを示す通し番号）を取ってセッションに覚えておき、レプリカで読む直前にその位置まで追いつくのを待たせる。全体を親側に寄せて負荷を集中させるのでも、一律に待たせて遅くするのでもなく、必要な読み取りだけを必要な分だけ待たせられるのが利点になる。記事の執筆時点でPostgreSQL 19はbeta3のため、本番投入はまだ先だ。

### [Static Allocation, Constant Work](https://matklad.github.io/2026/09/02/static-allocation-constant-work.html)
<!-- categories: Performance, Distributed Systems -->

信頼性の高いシステムを書くための2つの原則を、matklad氏が自身のブログで論じている。ひとつは「初期化以降は動的なメモリ確保をしない」こと。起動時に上限ぶんをまとめて確保し、それを超える要求は追加確保を試みずに拒否する。例として挙がっているのは`--orders-max=1_000_000`のような上限を持つ注文マッチングエンジンで、メモリ不足でシステム全体が落ちる事態を、個別の要求を断るという軽い失敗に置き換えられる。もうひとつは「常に同じだけの仕事をする」こと。注文を作ったり消したりせず、空き枠を「予約済み」という中立の状態として持ち、処理では常に全枠を舐める。無駄はあるが、負荷が変わってもP100（最悪ケースの応答時間）が平らなままになり、コンパイラの最適化やCPUの先読みも効きやすい。代わりに、上限をあらかじめ見積もる責任は設計者側に移る。

### [New things for regular expressions in PostgreSQL (pg_tre and pg_re2)](https://www.depesz.com/2026/08/25/new-things-for-regular-expressions-in-postgresql-pg_tre-and-pg_re2)
<!-- categories: PostgreSQL, Database -->

PostgreSQLの正規表現検索を速くする2つの拡張を、depesz氏が160万行のデータで実際に比べた。Greg Burd氏によるpg_treは、綴りの揺れをレーベンシュタイン距離（何文字直せば一致するかで測る近さ）で吸収するあいまい検索に向くが、インデックス作成に約7時間15分・サイズ21GBを要した。ClickHouseによるpg_re2は、Googleのre2ライブラリを使う速度重視の実装で、インデックス作成は約15分・サイズ2.9GBと桁違いに軽く、検索も単純なパターンなら約959ミリ秒で返る。比較対象として、インデックスなしの全件走査は約23秒、標準のPostgreSQL正規表現では約40秒かかっている。どちらも後読み`(?<=...)`には対応しないため、複雑なパターンを使っている環境では事前の確認が要る。

### [Implementing FMA and finding bugs in C and Rust standard libraries](https://shnatsel.github.io/implementing-fma-finding-bugs-in-std)
<!-- categories: Rust, C -->

Sergey Davidoff氏が、SIMDライブラリfearless_simd向けにFMA（`a * b + c`を丸め誤差1回で計算する演算。三角関数などの精度に効く）を実装する過程で、複数の標準ライブラリのバグを掘り当てた。見つかったのはRust標準ライブラリの`std::simd`と`f32::mul_add`、およびmusl libcの`fmaf()`で、いずれも極端に小さい値（非正規化数）の丸めを正しく扱えていなかった。musl側の該当コードは2005〜2011年頃のFreeBSD由来で、あちこちにコピーされて広まっていたという。影響が出るのはFMAをハードウェアで持たない環境に限られるため、AVX2非搭載の古いIntel系や32ビットARMが対象で、64ビットARMは当初からFMAを備えているので無関係だ。実装しようとして初めて見つかる種類の欠陥で、記事では再現する具体的な入力値も示されている。

EU域内でWebサービスやスマホアプリを出す企業が押さえるべき法制度を、クラスメソッドのDevelopersIOが整理した。よく話題になるEAA（欧州アクセシビリティ法）だけでなく、公共機関向けのWAD、雇用分野のEmployment Equality Directiveまで含めて、B2C・B2B・公共調達それぞれで何が要求されるのかを分けて説明している。実装面ではWCAGとEN 301 549を基準にした具体的な進め方に触れ、さらにEU主要10カ国の国内法・罰則・執行事例まで並べているのが実務向けだ。アクセシビリティを「やった方がよいこと」ではなく法的な要件として扱う地域が増えている以上、EU向けに何かを出す予定があるなら、設計の初期に読んでおく類の記事になる。

### [Accessible and Functional Quantity Spinbutton Pattern](https://dev.to/micaavigliano/accessible-and-functional-quantity-spinbutton-pattern-1945)
<!-- categories: Accessibility, HTML -->

買い物かごの個数入力のような「数値を上下ボタンで増減させる部品」を、支援技術から正しく読めるように作る方法を、著者のMica氏がReactの実例つきで解説した。比較しているのは2案で、ひとつはARIA（画面読み上げソフトに部品の役割を伝える追加情報）の公式ガイドに沿ってテキスト入力に`role="spinbutton"`と`aria-valuemin`などを自前で付ける方式、もうひとつは`<input type="number">`という標準の部品をそのまま使う方式だ。著者は「悪いARIAを書くくらいなら書かない方がまし」という原則を挙げて後者を推すが、Safari（WebKit）だけは標準の数値入力をスピンボタンとして認識しないため、結局`role="spinbutton"`を明示する必要があると指摘している。上下キーで増減、Homeで最小値、Endで最大値というキー操作の期待値と、NVDA・VoiceOver・TalkBackでの読み上げの違いまで踏み込んでいる。
