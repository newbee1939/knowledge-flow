### [エラーレスポンス設計の現在地2026](https://qiita.com/tatsuya582/items/e5c56a2f7b976cfc17ea)
<!-- categories: HTTP, Standards -->

API がエラーを返すときの作法を、ステータスコード・ヘッダー・本文の3層に分けて整理した記事。ステータスコードは監視やCDNなど本文を読まない仕組みが解釈する層なので、エラーを「200 OK」で返してはいけない、という原則から入る。400と422（形式が壊れているか、意味的に処理できないか）、401と403（そもそも誰か分からないか、権限が足りないか）の使い分けも具体的だ。ヘッダー層では、401には `WWW-Authenticate`、405には `Allow`、429と503には次にいつ試せばいいかを示す `Retry-After` を必ず付けるよう求めている。本文は RFC 9457（Problem Details）に沿って `type` / `title` / `status` / `detail` / `instance` を返し、クライアント側の分岐は文字列一致ではなく `type` で行う。スタックトレースや内部IDは `detail` に入れず、`instance` の相関IDからログを引く、という安全側の指針も明快だ。

### [Demystifying AI Agent Authentication & Authorization: OAuth 2.0](https://medium.com/google-cloud/demystifying-ai-agent-authentication-authorization-oauth-2-0-49cd56b89811)
<!-- categories: AI Agent, Security -->

AI エージェントに外部サービスを触らせるときの、認証（あなたは誰か）と認可（何をしてよいか）の設計指針。よくある失敗は、OAuth の「スコープ」を権限そのものだと思い込むことだという。スコープは利用者がどこまで同意したかの上限にすぎず、実際に読める・書けるかはサーバー側が別途 RBAC/ABAC で判断すべきで、`reports:read` のトークンを持っていても、社内ポリシーが特定ファイルを禁じていれば拒否されなければならない。設計はプラットフォーム層（IdP での本人確認）、エージェント層（そのエージェント自身の権限）、ツール層（外部APIごとの個別 OAuth）の3段構えを推奨している。安全策として、認可コードの横取りを防ぐ PKCE、企業の認証基盤にクライアントを自動登録する DCR、署名済み JWT を検証する SSA が必須項目に挙げられた。

### [Why Idempotency Matters More Than Retries in Microservices](https://hackernoon.com/why-idempotency-matters-more-than-retries-in-microservices)
<!-- categories: Distributed Systems, HTTP -->

サービス同士の通信で「時間切れ（タイムアウト）」が起きたとき、それは失敗ではなく「結果が分からない状態」だ、という指摘から始まる記事。注文サービスが決済サービスに支払いを頼み、返事が届かなかった場合、決済が拒否されたのか、処理中なのか、すでに完了しているのかを注文側は判別できない。ここでそのまま再送すると、単なる通信トラブルが二重決済という業務事故に化ける。解決策は、リクエストごとではなく「その支払い」に対して1つの識別子（`Idempotency-Key`）を割り当て、再送時も同じ鍵を使うこと。決済サービス側は鍵と一緒にリクエスト内容のハッシュを保存し、同じ鍵で金額が違うものが来たら別処理ではなく矛盾として弾く。記録の保持期間が短すぎると、遅れて届いた正当な再送が新規扱いになってしまう点にも注意を促している。

### [Speeding Up (small) Ruby Hashes](https://byroot.github.io/ruby/performance/2026/08/13/speeding-up-ruby-hashes.html)
<!-- categories: Ruby -->

Ruby のハッシュ（キーと値の対応表）は、要素が8個以下だとメモリ節約のため配列に近い形で持ち、探すときは先頭から順番に見ていく。そのため最後に入れたキーを引くと、先頭のキーより明らかに遅かった。著者は8バイト分の目印を「64ビットの整数1個」とみなし、足し算とビット演算だけで8個すべてを一度に照合する SWAR という手法を適用した。結果、位置0では毎秒1,400万回・位置7では900万回（1.58倍の差）だったのが、どの位置でも1,400万回で揃った。おまけに、要素が多いときに使う本来のハッシュテーブルより1.28倍速くなっており、小さなハッシュを大量に作る Ruby プログラムに広く効く改善だ。

### [Windows Defender脆弱性対処は不適切。新ゼロデイ脆弱性「ShieldBrake」](https://pc.watch.impress.co.jp/docs/news/2132712.html)
<!-- categories: Security, Windows, Microsoft -->

セキュリティ研究者の Nightmare Eclipse 氏が、Windows Defender の新しいゼロデイ脆弱性「ShieldBrake」を公開した。ゼロデイとは、修正プログラムが出る前に手口が知られてしまった弱点のことだ。厄介なのは、これが以前報告された「RoguePlanet」への Microsoft の修正が不十分だったために成立している点で、公式パッチを当てていてもすり抜けられてしまう。研究者は「月例パッチは無意味」とまで表現している。確認されているのは Windows 11 25H2、Windows Server 2025、Windows Insider の Canary チャネルで、Windows 10 は検証対象外ながら OS 自体は影響を受ける可能性があるとされる。現時点で有効な回避策は示されておらず、Microsoft からの正式情報を待つ状況だ。

### [Google is making private AI practical with homomorphic encryption](https://blog.google/security/how-google-is-making-private-ai-practical-with-homomorphic-encryption)
<!-- categories: Security, Google, AI -->

Google が、暗号を解かないまま計算する「準同型暗号」を実用化するためのオープンソースのコンパイラ「HEIR」を公開した。普通はサーバー側でデータを復号しないと処理できないが、準同型暗号なら中身を見ないまま計算し、暗号化された答えを返せる。たとえば、利用者の好みをサーバーに知られないままおすすめを出す、といったことが可能になる。Google は、おすすめ配信・クレジットカードの不正検知・暗号化された通信の異常検知・音声の呼び出し語検出という4つの実装例を示した。この技術の最大の弱点は計算量の重さだが、Google に加え Belfort Labs や Niobium が専用ハードウェアを開発中で、HEIR 自体も専門家でなくても使える「ワンクリック」の道具を目指している。

### [Xがタイムライン表示アルゴリズムをオープンソース化＆自分のアカウントの扱いを可視化できるツールも試験提供開始](https://gigazine.net/news/20260814-x-timeline-algorithm)
<!-- categories: OSS, Business -->

X が「おすすめ」タイムラインの中身を決めるアルゴリズムを公開した。公開対象は、投稿をおすすめに載せるかどうかの判定と、載せた投稿の並び順を決める部分の2つだ。あわせて「Under the hood」という機能の試験提供も始まり、自分のアカウントや投稿がシステム内でどう扱われているかを確認できる。対象は月10回以上投稿し、利用開始から1年以上経ったランダムな試験グループで、統計情報を JSON 形式でダウンロードして AI に分析させることもできる。2023年の公開時は Twitter 公式リポジトリだったが、今回は SpaceXAI の GitHub リポジトリが置き場所となった。X は今後さらにソースコード全体の公開を計画しているという。

### [Databricks wanted to raise $1B, investors wanted $15B. It settled on $5B at a $190B valuation.](https://techcrunch.com/2026/08/13/databricks-wanted-to-raise-1b-investors-wanted-15b-it-settled-on-5b-at-a-190b-valuation)
<!-- categories: Business -->

データ基盤大手の Databricks が、企業価値1,900億ドルの評価で50億ドルを調達した。当初の予定は10億ドルだったが、報道をきっかけに投資家から150億ドル分の申し込みが集まり、既存投資家への配慮もあって増額したという経緯だ。主幹事は Coatue で、Blackstone、MGX、T. Rowe Price 傘下各社など約20社が参加した。年間の経常収益は70億ドル（前年比80%成長）、主力のクラウドデータウェアハウスが15億ドル（同100%成長）、新製品 Lakebase が1億ドルという規模感で、調達資金は100人規模の研究チーム、クラウド各社との契約、企業買収に充てる。同社は過去20か月で計200億ドルを調達しており、AI 事業がいかに資本を食うかを示す数字でもある。

### [Microsoft、個人・ビジネスCopilotアプリを統合。Deep Researchなど廃止](https://pc.watch.impress.co.jp/docs/news/2132756.html)
<!-- categories: Microsoft, Business -->

Microsoft が、個人向けの「Microsoft Copilot」と職場・学校向けの「Microsoft 365 Copilot」を1つのアプリに統合する。新アプリでは個人アカウントと職場アカウントの両方でサインインでき、Word や Excel、Outlook に直接つなげられるようになる。移行は基本的に自動で、Microsoft 365 Copilot の利用者にはアプリ名とアイコンが変わった程度に見えるという。一方、2026年8月18日に3つの機能が廃止される点は注意が必要だ。グループチャットは1対1のみになり過去の添付ファイルにアクセスできなくなる、ポッドキャスト機能は消えるため作成済みの音声は事前にダウンロードが必要、そして深掘り調査の「Deep Research」は一般提供を終了する（Microsoft 365 Premium 契約者は「Researcher」機能で代替）。
