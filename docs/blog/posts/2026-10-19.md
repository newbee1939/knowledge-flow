### [マイクロソフト、.NETのツールチェーンマネージャ「dotnetup」プレビュー公開。複数バージョンの.NET環境を管理可能](https://www.publickey1.jp/blog/26/netdotnetupnet.html)

Publickey によると、Microsoft が .NET の開発道具一式を管理する「dotnetup」を試験公開した。Rust の rustup や Node.js の nvm にあたる道具で、複数の版を干渉させずに同居させられる。管理者権限が要らず、Windows・Mac・Linux で同じように使える。プロジェクトごとに .NET の版を変えたい開発者の手間が減る。

### [Lambdaが3種類になったみたいなので、全部試してみた](https://qiita.com/maeda-kazutoshi/items/4674e080c2ce3d53c809)
<!-- categories: AWS -->

AWS Lambda が3種類になったのを受け、1つのアプリで全部を使い分けた記事が Qiita に投稿された。従来型はファイルの到着などをきっかけに動き、[Web Functions](/blog/2026-10-13/#announcing-aws-lambda-web-functions--amazon-web-services)は Web アプリをそのまま載せられる。MicroVMs は隔離された仮想マシンで、AIが書いた信用できないコードを動かす役に使った。丸1日動かした費用は約20セントで、大半が MicroVMs の分だったという。

### [トレーシング基盤なしで「どこが遅いか」を SQL で探す：gospan で net/http の span を SQLite に溜める](https://zenn.dev/nonejp/articles/c7dd2859872f9d)
<!-- categories: Go, Observability, SQLite -->

Go のサーバーで「どの処理が遅いか」を、専用の監視基盤なしで調べるライブラリ gospan を Zenn の記事が紹介した。処理ごとの所要時間の記録（スパン）を、同じプロセスの中で SQLite の表に貯めていく。あとは SQL で集計すれば、特定の条件のリクエストだけ遅いといった傾向が見つかる。複数のサービスをまたぐ追跡はできないため、その用途では OpenTelemetry を勧めている。

### [A New Way to Think About Borrow Checking (In Reverse)](https://verdagon.dev/blog/reverse-borrow-checking)
<!-- categories: Rust -->

関数を下から上へ逆向きにたどってメモリ安全性を確かめる方法を、verdagon.dev の著者が解説した。借用検査とは、誰かが使っているデータを横から書き換えていないかを、コンパイル時に調べる仕組みだ。Rust の検査は前から順に進むが、逆向きなら変数を最後に使う場所に最初に出会える。記録の付け方が単純になる一方、ループには追加の工夫が要るという。

Vite のアプリを Cloudflare へ公開する「Void」を、azukiazusa.dev がメモアプリで試した。コード中の import から必要なデータベースなどを読み取り、設定ファイルなしで用意してくれる。void deploy の1コマンドで、データベースの作成から公開までが済む。[先日公開された Void](/blog/2026-10-17/#deploy-with-void)の使い心地を、実際の手順で確かめられる。

### [One Request, Many Callers: Coalescing Duplicate fetch() Calls in JavaScript](https://dev.to/zainalsaadi/one-request-many-callers-coalescing-duplicate-fetch-calls-in-javascript-13k2)
<!-- categories: JavaScript, Performance -->

同じ API への fetch が一瞬に何度も飛ぶ無駄を、1回にまとめる手法を Dev.to の記事が解説した。通信中の要求を URL ごとに覚えておき、後から来た呼び出しには同じ Promise（あとで結果が届く約束の箱）を返す。失敗した結果は取っておかず、終わった要求はすぐ消すのが要点だ。POST のようにデータを書き換える要求には使ってはいけないと注意している。

### [【Vite】ビルド時に出た Error: Cannot find native binding. npm has a bug related to optional dependenciesを解決](https://qiita.com/ryu0947/items/03af280e053c5d967168)
<!-- categories: Vite, npm -->

Vite で「Cannot find native binding」エラーが出たときの対処を、Qiita の記事がまとめた。原因は、依存を入れたときと後で固定した Node.js の版が食い違っていたことだった。node_modules と package-lock.json を消して入れ直せば直る。新しく作るときは、Node.js の版を先に決めてから npm install するのが安全だという。
